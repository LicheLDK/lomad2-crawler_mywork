## 1. 선행 확인 필요 — 착수 전 담당자 결정 사항

아래 4건은 코드만 보고 결정할 수 없다. **결정 전에는 해당 항목을 구현하지 말고 질문한다.**

### D1. Investigation 자동 생성의 정본 경로 (→ TASK 0-1 차단)

현재 두 경로가 같은 케이스를 만들려 한다.

| 경로                       | 위치                                                                        | 점수        |
| -------------------------- | --------------------------------------------------------------------------- | ----------- |
| ① 크롤 완료 직후 (Worker)  | `src/crawler/crawler.service.ts` `executeCrawl()` 말미                      | 휴리스틱    |
| ② Search Job 완료 후 (API) | `src/modules/search-job/search-job.service.ts` `triggerAutoInvestigation()` | AI Matching |

①이 먼저 실행되어 케이스를 만들고, ②는 `resultId` unique 중복으로 skip된다.

**결정할 것**: 다음 중 하나를 선택.

- **(A) AI 단일화** — ①에서 자동 생성을 제거한다. 단, `POST /api/search`·`POST /api/crawl`로 직접 검색한 경우에는 케이스가 생성되지 않게 된다. 이를 허용하는지 확인 필요.
- **(B) upsert** — ①은 유지하고, ②가 기존 케이스의 `aiScore`·timeline·recommendation을 **갱신**하도록 바꾼다. 직접 검색 경로도 케이스를 얻는다.

> 권고: **(B)**. 기능 삭제가 없고 직접 검색 경로도 보존된다.

### D2. brand/model 저장이 "주문 마스터 복제 금지" 원칙 위반인지 (→ TASK 0-2 차단)

`search-job.service.ts` `create()`는 `brand`·`modelName`·`option`·`color`를 주석과 함께 의도적으로 `null` 저장한다.

**결정할 것**: 원칙의 범위.

- **(A) 스냅샷 허용** — 브랜드·모델은 상품 속성이므로 `productName`과 동일하게 검색 실행 스냅샷으로 DB 저장한다. 구현이 단순하고 재조회 없이 재현 가능하다.
- **(B) 영속화 금지** — DB에는 저장하지 않고, `searchInput`을 `create()` → `runSearch()` → `triggerAutoInvestigation()`까지 메모리로 전달한다. 원칙을 엄격히 지킨다.

> 권고: **(A)**. `productName`을 이미 스냅샷으로 저장하고 있어 일관성이 있다. 단 고객 개인정보(`customerName`)는 계속 `null` 유지.

### D3. "오늘 Investigation" 타일의 처리 방식 (→ TASK 0-3 일부 차단)

현재 조사 케이스 **건수**를 반환하는 API가 없다(`GET /api/investigations`는 목록만).

**결정할 것**:

- **(A) 레이블 정정** — 타일을 "오늘 수집 결과"로 바꾸고 실제 의미(`last24h.results`)와 일치시킨다. P0 범위 내.
- **(B) 카운트 API 신설** — 백엔드에 케이스 집계 엔드포인트를 추가한다. **P0 범위 초과** → 우선순위 B로 이관.

> 권고: **(A)**로 P0를 마감하고, 우선순위 D-1(Investigation 실 API 전환) 시점에 실제 케이스 수로 교체.

### D4. ESLint 도입 정책 (→ TASK 0-5 차단)

지금까지 lint를 한 번도 실행한 적이 없어, 켜는 순간 기존 코드 위반이 대량 발생한다. `--fix`를 전체에 돌리면 커밋 하나가 수백 파일이 되어 리뷰가 불가능해진다.

**결정할 것**:

- **(A) 단계적 (권고)** — 기존 코드 위반은 `warn`, 신규/변경 파일만 `error`. CI는 `--max-warnings` 상한을 두고 점진적으로 낮춘다.
- **(B) 일괄 정리** — `--fix` 전체 적용 후 별도 커밋으로 분리. 리뷰 부담이 크다.

## TASK 0-1. Investigation 자동 생성 경로 단일화

**선행**: D1 결정 필수  
**우선순위 근거**: v3 §7.2 N1 (심각) — AI 매칭 비용을 지불하고도 결과가 케이스에 반영되지 않는다

### 변경 대상

| 파일                                                      | 내용                                                                                 |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `src/modules/investigation/investigation.service.ts`      | `autoCreateFromSearch()` — 중복 판정 분기                                            |
| `src/crawler/crawler.service.ts`                          | `executeCrawl()` 말미의 자동 생성 호출 (선택 A인 경우)                               |
| `src/database/entities/investigation-case.entity.ts`      | `scoreSource` 필드 추가 (P0에서는 컬럼 추가 없이 기존 `metadata`/timeline 활용 권장) |
| `src/modules/investigation/investigation.service.spec.ts` | **신규**                                                                             |

### 구현 방향 (D1=B, upsert 선택 시)

1. `autoCreateFromSearch()`에 점수 출처를 구분할 입력을 받는다 (예: `aiResults`가 있으면 AI 경로).
2. 기존 케이스가 있고 이번 호출이 AI 경로이면 **skip 대신 갱신**한다. 갱신 대상: AI 점수, Rule Engine 평가 결과, AI 분석/추천 timeline 항목.
3. 기존 케이스가 있고 이번 호출이 휴리스틱 경로이면 기존 동작(skip)을 유지한다.
4. 사람이 이미 상태를 바꾼 케이스(`Open`이 아닌 케이스)는 **덮어쓰지 않는다.** 조사자가 판단한 내용이 AI 재계산으로 되돌아가면 안 된다.
5. 점수 출처를 timeline에 남긴다 (예: `"AI 매칭 점수로 갱신"`).

### 완료 조건

- [ ] 휴리스틱으로 먼저 생성된 케이스에 AI 결과가 도착하면 점수·timeline이 갱신된다
- [ ] 사람이 상태를 변경한 케이스는 AI 재평가로 덮어써지지 않는다
- [ ] Rule Engine의 `exclude` 판정이 AI 점수 기준으로 동작한다
- [ ] 직접 검색(`POST /api/search`) 경로에서도 케이스가 계속 생성된다 (D1=B)
- [ ] 신규 spec이 위 4개를 고정한다

### 검증

```bash
npm run build
npx jest --runInBand            # 신규 spec 포함, 기존 52건 회귀 없음
```

**런타임 재현 (가능하면 권장)**: `npm run infra:up` 후 검색 1건을 실행해, 생성된 `investigation_cases` 행의 점수가 AI 매칭 결과와 일치하는지 확인한다.

## TASK 0-2. AI 매칭에 brand/model 실제 전달

**선행**: D2 결정 필수  
**우선순위 근거**: v3 §7.2 N2 (심각) — 매칭에 가장 강한 신호가 항상 비어 전달된다

### 변경 대상

| 파일                                           | 내용                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------- |
| `src/modules/search-job/search-job.service.ts` | `create()`의 `null` 저장부, `triggerAutoInvestigation()`의 매칭 입력 구성 |
| `src/database/entities/search-job.entity.ts`   | (D2=A인 경우) 기존 컬럼 재사용 — **신규 컬럼 추가 불필요**                |

### 구현 방향

- **D2=A (스냅샷 허용)**: `create()`에서 `brand`, `modelName`, `option`, `color`에 `searchInput`의 값을 저장한다. `contractNo`·`customerName`은 계속 `null` 유지. 컬럼이 이미 존재하므로 마이그레이션 불필요.

### 완료 조건

- [ ] `triggerAutoInvestigation()`의 AI 매칭 입력에 브랜드·모델이 실제 값으로 채워진다
- [ ] 고객 개인정보(`customerName`, `contractNo`)는 여전히 저장/전달되지 않는다
- [ ] BackOffice에서 브랜드·모델이 없는 주문도 오류 없이 처리된다 (null 허용)
- [ ] 매칭 입력 필드가 채워지는지 검증하는 spec이 있다

## TASK 0-4. Investigation 기본 필터와 사이드바 활성 일치

**선행**: 없음 (독립)  
**우선순위 근거**: v3 §7.3 U2, U3 — 사이드바는 Open을 강조하는데 목록은 전체가 표시된다

### 현재 불일치

- `navigation.ts` `childPathActive()`의 `defaults`는 쿼리 없는 `/investigation`을 **`status=Open`으로 간주**
- `CaseListPage`는 쿼리가 없으면 `statusFilter = ''`, 즉 **전체 표시**
- Overview Quick link가 `/investigation`(쿼리 없음)으로 이동 → 불일치 발생
- 페이지 내 "상태 전체" 선택 시에도 동일 불일치
- 알 수 없는 `?status=` 값이 오면 직전 필터가 그대로 남고 URL 정규화가 없다

### 변경 대상

| 파일                                                         | 내용                                                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `web/src/config/navigation.ts`                               | `NavChild`에 `isDefault?: boolean` 추가, `childPathActive()`의 하드코딩 `defaults` 맵 제거 |
| `web/src/features/investigation/components/CaseListPage.tsx` | 알 수 없는 status 정규화                                                                   |
| `web/src/pages/OverviewPage.tsx`                             | Quick link 경로를 기본 쿼리 포함으로 변경 (선택)                                           |

### 구현 방향

1. 기본 쿼리를 `NAV_SECTIONS`의 `NavChild` 속성으로 옮겨 **단일 소스**로 만든다. 현재는 `navigation.ts`의 맵과 각 페이지 fallback 두 곳에서 이중 관리되고 있다.
2. `/investigation`의 의미를 하나로 확정한다. 「전체」로 할 경우 기본 표시 항목을 두지 않고, 「Open」으로 할 경우 페이지 기본값을 `'Open'`으로 바꾼다.
3. 알 수 없는 status 값은 기본값으로 정규화하고 `setSearchParams(..., { replace: true })`로 URL을 정리한다.
4. 기존 Rental/Analytics/System의 기본값(`contracts`, `search`, `worker`)은 **현재 페이지 fallback과 일치하므로 동작을 바꾸지 않는다.**

### 완료 조건

- [ ] 쿼리 없는 `/investigation` 진입 시 사이드바 활성 항목과 목록 내용이 일치한다
- [ ] 페이지 내 "상태 전체" 선택 시에도 일치한다
- [ ] `?status=존재하지않는값` 진입 시 기본값으로 정규화되고 URL이 정리된다
- [ ] Rental·Analytics·System 탭 활성 표시에 회귀가 없다
- [ ] 기본 쿼리 정의가 `navigation.ts` 한 곳에만 존재한다

